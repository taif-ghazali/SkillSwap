# SkillSwap Android: Production Backend Integration, Full Live QA & Release Readiness

You are taking ownership of the final production integration and testing phase of the SkillSwap Android application.

This is NOT a redesign or a fresh implementation. The Android application has already been developed in MIT App Inventor, transformed using the Figma design reference, and functionally integrated with the development backend.

Your responsibility is to take the FINALIZED `.aia` project, connect it to the NEW PRODUCTION Google Apps Script backend, comprehensively test the entire application against the live production infrastructure, resolve any genuine integration defects, and prepare a release-ready Android APK.

The objective is a working, production-connected Android application, not merely a successful build.

---

## 1. Initial Project Reconnaissance

Before modifying anything:

1. Inspect the complete project directory and understand its structure.
2. Locate the finalized Figma-driven MIT App Inventor `.aia` project.
3. Locate the original AIA backup and previously reviewed AIA versions.
4. Locate the production backend source, deployment documentation, website implementation, API contracts, automated tests and previous testing reports.
5. Identify the exact production Google Apps Script `/exec` endpoint and corresponding API key.
6. Understand the backend request/response contract by inspecting the actual production `Code.gs`.
7. Identify any differences between the QA backend and production backend.
8. Establish which AIA file is the authoritative final design.

Do not assume that the latest modified file is necessarily the final version.

Preserve the original AIA and create a separate working copy for production integration.

Do not modify the website frontend or unrelated project components.

## 2. Production Backend Integration

The Android application and website must use the SAME production backend and production Google Spreadsheet.

Configure the finalized AIA:

- `global apiUrl`: production Apps Script `/exec` URL.
- `global apiKey`: matching production backend credential.

Use the existing API contract. Do not invent new endpoints, parameter names or response formats.

Inspect every `callApi` invocation and ensure that:

- Correct actions are dispatched.
- Required parameters are supplied.
- Responses are parsed correctly.
- API errors are handled gracefully.
- Network timeouts do not leave the UI permanently disabled.
- Duplicate requests and double submissions are prevented.
- Stale responses cannot overwrite newer application state.

Verify that no QA endpoint or development credential remains in the production application.

IMPORTANT SECURITY REQUIREMENT:

The production API key must never appear in committed source, public reports, terminal output or screenshots.

The current MIT App Inventor architecture may embed the key in the AIA/APK. Explicitly document this limitation and assess whether a server-side proxy is needed for public distribution. Do not claim that an embedded key is secure.

Do not change the backend authentication contract or rotate credentials without authorization.

## 4. Full End-to-End Functional Testing

Test every core workflow against the production backend.

### A. Authentication and registration
- University email validation.
- New user registration.
- Initial credit allocation.
- Existing user login.
- Duplicate registration handling.
- Correct retrieval of existing user balances.

### B. Profile management
- Save nickname.
- Save teaching skills/offers.
- Save learning preferences/wants.
- Refresh and retrieve saved information.
- Sign out and sign back in.
- Verify profile persistence.

### C. Tutor discovery
- Search by skill.
- Retrieve available teaching slots.
- Correct tutor and slot information.
- Exclude inappropriate or unavailable slots.
- Verify date and time formatting, especially early-morning times such as 02:45 and 09:05.

### D. Publishing teaching sessions
- Validate skill, date, time and venue.
- Publish a new teaching slot.
- Verify the corresponding production Sheets row.
- Verify that the slot appears in discovery.
- Reject invalid or incomplete submissions.
- Prevent accidental duplicate publication.

### E. Booking
- Book an available session.
- Display the academic integrity notice.
- Reserve exactly one learner credit.
- Verify slot status and learner identity.
- Prevent double booking.
- Verify insufficient-credit handling.

### F. Cancellation
- Verify cancellation eligibility.
- Enforce the backend's FR-6 two-hour cancellation restriction.
- Restore the slot to open status where permitted.
- Verify reservation and balance restoration.
- Reject unauthorized cancellation.

### G. Session confirmations
- Tutor confirmation.
- Learner confirmation.
- Pending confirmation state.
- Both-party confirmation.
- Ensure that credit transfer occurs exactly once.

### H. Wallet and ledger
- Verify learner debit.
- Verify tutor credit.
- Verify wallet balances.
- Verify ledger entries.
- Ensure balances remain consistent after refresh and re-login.
- Test repeated confirmation requests for duplicate-credit protection.

### I. Ratings and reviews
- Submit a rating between 1 and 5.
- Reject invalid ratings.
- Prevent duplicate ratings.
- Verify saved ratings in the production spreadsheet.
- Verify tutor profile rating and review count where supported.

### J. Session management
- Verify active, open, booked and completed session listings.
- Verify tutor and learner perspectives.
- Check session status after cancellation and confirmation.
- Ensure all displayed information agrees with the backend.

## 5. Production Database Integrity

The production database is authoritative.

Inspect the following tabs:

- Users
- Slots
- Ledger
- Ratings

Verify:

- Column headers match the expected schema.
- No accidental QA data has been imported.
- No duplicate transactions have been created.
- No negative or inconsistent credit balances exist.
- No orphaned ledger entries exist.
- Slot statuses agree with their transaction history.

IMPORTANT:

Do not run initialization/reset routines on an existing production database.

Do not delete production users, slots, ratings or ledger records.

Do not insert arbitrary test accounts into production.

For destructive or transactional testing, use explicitly authorized test accounts and a disposable test slot. If these are unavailable, stop before creating production records and report exactly what authorization is needed.

Clean up only records explicitly designated as disposable QA records, and only after verifying their identities and obtaining authorization.
