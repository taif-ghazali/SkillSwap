# SkillSwap deployment preparation

Status: prepared locally; no deployment or live endpoint tests have been performed.

## Configuration and deployment

1. Create/open the Google Sheet that both clients will use. Open Extensions > Apps Script so the script is bound to that sheet.
2. Copy `Code.gs` and `PrepareDeployment.gs`. `InitSheet.gs` is optional and contains demo data; do not run `resetDemoDatabase()` on a real database. The former `setupDatabase()` stops with an explanation instead of clearing rows.
3. In project settings, show `appsscript.json` and copy the supplied manifest. It sets Asia/Kolkata and enables the **Google Sheets API v4** advanced service (`Sheets`). Check Services in the editor. If using a standard Google Cloud project, also enable Google Sheets API in that project's Cloud console. [Google service setup](https://developers.google.com/apps-script/advanced/sheets).
4. `Code.gs` contains `const KEY = 'team-secret-123';`. That is the existing expected key, not a newly invented deployment credential. The reviewed AIA uses the same value. If the team changes it, update the website and AIA together. No key is generated by the preparation routine.
5. Run `prepareDeployment()` and authorize the spreadsheet permissions. It validates existing headers before making changes, creates missing empty tabs, formats Slots date/time columns as plain text, and preserves all records. Run it again safely if needed.
6. Review the deployment permissions, then deploy a web app: execute as the owner; access Anyone as required by these clients. Record the generated `/exec` URL. No URL has been assumed or embedded in this repository.
7. In the reviewed AIA, set global `apiUrl` to that exact `/exec` URL; retain/set global `apiKey` to the matching KEY. In the website's backend settings use the same URL and key. This is how both clients reach the same spreadsheet.
8. Test ping first, then T1-T8 on a separate test sheet/deployment with two test accounts. Confirm actual sheet rows and ledger entries, then do a two-device Android smoke test. No mock data is used by the Android project.
9. After a backend code change, update the deployment to a new version. Saving the script alone does not update an existing versioned deployment.

The shared key/email scheme is the existing course-project contract; it does not verify mailbox ownership. Do not treat it as university SSO. Keep direct editing of balances/ledger restricted to the team and avoid editing credit rows while requests run.

## Existing API contract (unchanged)

Every request includes `key`, `action`, and (except ping) `email`. GET query strings, URL-encoded POST parameters, and JSON POST bodies retain the same action names and envelopes: `{ "action": "...", "data": ... }`; failures use `data.error`.

| Action | Extra parameters | Success data |
| --- | --- | --- |
| ping | none | status, timestamp, university |
| login | nick | email, nick, credits, isNew, offers[], wants[] |
| profile | offers, wants; optional nick | ok, nick, offers, wants |
| search | skill | array of slots |
| publish | skill, date, time, place | ok, slotId |
| book | slot | ok |
| cancel | slot | ok |
| confirm | slot | ok, transferred |
| rate | slot, stars | ok, stars |
| mine | none | credits, nick, slots[] |
| report | target, reason | ok, reportId |
| dashboard | none | usersCount, slotsCount, completedCount, bookedCount, openCount, popularSkills |

Dates are campus IST `yyyy-MM-dd`; times are 24-hour `HH:mm`. Publish rejects impossible/past dates and private/unrecognized venues. Allowed venue descriptions include library, lab/labs/laboratory, canteen, foyer, seminar hall, amphitheatre, or Online/https links; private/home/hostel descriptions are rejected. Booking rejects expired/own/unavailable slots. Cancellation includes the exact two-hour boundary. Confirmation is permitted after the session start. Ratings require an integer 1-5, a completed session, a participant and no prior rating by that participant. These validations keep the same parameters and error envelope.

Credit checks and mutations run under the script lock. Both confirmations trigger a single Sheets `batchUpdate` containing learner debit, tutor credit, done status and ledger append. A failed batch leaves those changes unapplied; a retry can complete it. A successful batch makes subsequent confirmation fail as already completed. [Google atomic batch guarantee](https://developers.google.com/workspace/sheets/api/guides/batch). Use the same bound script deployment for both clients so they share the lock.

## Reproduce local checks and Android build

From the project directory:

```powershell
npm test
npm run build
npm run build:android-source
python tools/validate_android.py
```

Node runs the actual Code.gs in an isolated Sheets/service adapter; this does not contact Google. The website tests use its existing mock service. Neither proves live integration.

Import `output/android/SkillSwap_MiniProject_Team_Reviewed.aia` into MIT App Inventor, configure its URL, review Blocks warnings, connect Companion and exercise all six pages. Then use Build > Android App (.apk), install on two Android devices and repeat T1-T8. [Official APK packaging instructions](https://appinventor.mit.edu/explore/save-your-app).

No App Inventor compiler/build server or signed-in build session is configured here. An APK has not been produced, and AIA structural validation is not compilation or device testing.
